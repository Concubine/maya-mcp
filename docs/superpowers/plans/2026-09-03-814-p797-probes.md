## C. retarget_clip's .fbx route — FIXED (it had never run live)

Every assumption the route was written on was refuted:

| assumption | measured |
|---|---|
| the file command's `namespace=` flag puts the import in `ns` | fbxmaya applies it as its own request → nodes land in `ns1` (P4); setting the CURRENT namespace lands them in `ns` (P5) |
| an import creates the file's joints | default `FBXImportMode` is **merge**: with a same-named rig in the scene, all 14,220 keys were written onto the TARGET RIG and no joint was created (P3); the route then refused "imported no joints" with the caller's rig animated |
| the scene time unit reflects the file's rate after import | it does not; a 60 fps take in a 24 fps scene sits at fractional frames 0–62.8 (C3, P2b); `FBXImportSetMayaFrameRate -v true` changed nothing (P2) |
| scaling the imported root matches the source to the target | fbxmaya's unit conversion is a **scale of 100 on the root joint itself**; writing the factor replaced it (gate run 1: pelvis path 73,930 for a 3.8-unit walk); a node's own scale does not move its own translation (run 2: still 200×); `cmds.group(roots)` pivots at the members' bbox centre so the scale shrank the source in place at world (93, 56, -187) and the target's hips followed it there (run 3: 106×) |

Shipped in `handlers/retarget.py`: `_import_fbx_source` (forces `add`, sets the
current namespace, restores both on the error path, parents the roots under an
EMPTY group at the origin inside `ns`), `_fbx_source_fps` (rate from key
spacing through the current unit; refuses a rate Maya has no unit for),
`_scale_source` (multiplies the existing scale). The route sets the scene to
the file's unit before reading the range. Row 25 (`fps` refused on .fbx)
stands. 7 tests in `TestTheFbxRouteReadsTheFileNotTheScene`.

Gate `evals/p797_rows_live.py` **15/15**: the FBX take of a BVH walk lands on a
