# #820 — undo and redo, measured for the first time

Redmine #820, second item of the #818 audit. `undo`/`redo` had never been sent
to a real Maya; every recovery path assumed one tool call = one undo step and
redo restores it. Probes (kept): `evals/undo_probe_820.py`,
`evals/undo_probe_820b.py`, `evals/undo_boot_timeline_820.py`; findings under
`evals/undo_probe_820/`. Maya 2027, agent 9878, repo cwd.

## What held

The per-request `undoInfo` chunk works: eight mutating calls (create,
transform, create, assign_material, combine, deform, execute_python ×3
objects, delete) each left one `maya-mcp` chunk; undoing them one at a time
returned exactly the pre-call scene each time, redo returned each post-call
scene, the auto-checkpoint added no step, and a capture added none.

## What the probes refuted — four measured facts

1. **`cmds.undo()` / `cmds.redo()` on an empty queue do not raise.** They
   return None / the linear unit. The handlers' `except RuntimeError: break`
   was dead code; they counted attempts, so `undo` after `new_scene` reported
   `undone: 1` and `redo` past the end reported 3. (The session fake's own
   comment had refused to guess this; now it is measured.)
2. **Maya's own callbacks push entries that change nothing:**
   `selectionMaskResetAll` (deferred, after any call that touched the
   selection), `hikDefinitionFileNewCallback;` (after a new file),
   `autoLoadPlugin("", …)` and `mtoa.cmds.registerArnoldRenderer._register`
   (boot), and a nameless entry `new_scene` leaves at the bottom. Walking the
   queue and undoing each changed no object.
3. **A pending deferred callback runs inside whatever chunk opens next.** A
   query-only execute_python then closes a non-empty `maya-mcp` chunk that
   reads as a real step. First seen when the gate's own state queries minted
   phantom steps.
4. **`undoQueueEmpty` reads True with entries still queued** once Maya has
   processed idle events between requests; the first gate run stopped on it
   with a cube standing. The entry NAME is reliable; the bottom is nameless.
5. **A plugin load flushes the undo queue.** Timeline from the moment the
   port listened: plugins 16 → 25 → 41 → 53 over ~7 s, and every request
   chunk recorded before ~8 s was gone; every one after survived. In that
   window the toolbox accepted edits that could not be undone.

## What shipped

- `session._walk_queue`: real steps only — steps over `is_no_op_entry` names
  (exact set + the `autoLoadPlugin(` / `mtoa.` prefixes) without counting
  them, stops on an EMPTY NAME (never the empty flag). Results gain
  `skipped` and `queue_empty`. `UndoResult` fields; protocol.md rows.
- `maya_mcp_plugin._undo_hooks`: `maya.utils.processIdleEvents()` before
  `openChunk`, so callbacks land as their own entries, never inside a chunk.
- `maya_mcp_plugin.start_server`: inside Maya, defers the bind until the
  loaded-plugin count has held still for `AUTOLOAD_SETTLE_S` = 1.5 s
  (re-deferred through a timer + `executeDeferred`); headless binds at once.
  Measured after: the port listens ~20 s after launch (was ~7) with all 53
  plugins loaded, and every chunk from the first request survives.
- Session fake remodelled as a named queue whose undo/redo do not raise;
  7 tests in test_session, 3 in test_plugin_e2e.

## Gate

`evals/undo_redo_live.py` **10/10** (no captures): eight single undos each
return the exact pre-call scene (the first create included — empty again),
exactly eight `maya-mcp` chunks on the queue with the noise below them, undo
past the end 0 / queue_empty, eight single redos exact, redo past the end 0,
deform-with-checkpoint undone in one, undo after new_scene 0. Regression:
`evals/recipe_orphans_live.py` 20/20 on the same build.

## Note

The `selectionMaskResetAll` entries appear ONLY when Maya idles between
requests — a gate that fires requests back to back never sees them, which is
why probe 1 saw the failure and a fast rerun did not. The gate sleeps 0.8 s
after every call on purpose.
