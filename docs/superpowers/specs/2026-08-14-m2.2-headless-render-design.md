# M2.2 — the headless render path

**Status:** approved design, not yet planned
**Ticket:** redmine #584 (project 35, `maya-mcp`)
**Follows:** M2 "eyes & skin" (#581, merged `fff61e7`) and M2.1 (#583, merged `c8ed348`)
**Evidence:** `evals/render_paths_probe.py`, `evals/arnold_transmission_probe.py` (commit `05bbcb0`)

---

## 1. Why this exists

Two problems from the gem-brute art run converge on one missing capability.

**The viewport cannot judge transmissive materials.** M2.1 added
`transmission` / `transmissionColor` / `ior` and they are set correctly — but
VP2 draws transmission as plain transparency, with no tinting and no
refraction. A diamond brute and a plastic brute look nearly identical in a
capture. No capture mode fixes it: the renderer is the limit, not the flags.

**An agent-launched Maya renders nothing.** Established in #577: it answers
every command, but `MayaWindow visible=False` means every playblast comes back
fully transparent. Every pixel check therefore needed the user.

The probe run closed both in principle. `playblast` reads the *viewport*, so it
needs a mapped window and inherits VP2's approximations; `cmds.render` goes
through the render pipeline and needs neither. Measured on an agent-launched
Maya: a lit sphere at 9416 opaque pixels of 65536, 1886 distinct colours.
Arnold is installed and renders real refraction headless — a transmissive
octahedron is structurally different from an opaque one where VP2 draws both as
near-identical grey.

What is missing is the tool. This milestone is the wrapper, not the discovery.

---

## 2. Boundary

**In:** one new tool, `maya_render_scene`, and the plugin handler behind it.

**Out, deliberately:**

- A `renderer=` passthrough on `capture_viewport` / `capture_turntable`. The
  params diverge (samples and light rigs are renderer concepts; wireframe
  overlay and display-lights modes are viewport concepts), and folding two
  backends into the tool the whole judging loop depends on is a risk taken for
  convenience. Revisit once `render_scene` has run live for a while.
- `ogsRender`. Still untested — the probe passed a bad `enableSSAO` flag and
  errored before rendering. It may be a faster hw2 route; it is a ticket note,
  not code.
- Animation, sequences, AOVs, denoising, render layers.

`capture_viewport` keeps its job: the fast viewport eye, for shape and
composition, on a Maya with a mapped window. `render_scene` is the slow
truthful one: correct light transport, works with no window at all.

## 3. The tool

`maya_render_scene(angles, renderer, resolution, isolate, samples, fallback_light)`

| param | default | notes |
|---|---|---|
| `angles` | `["three_quarter"]` | Same vocabulary as `capture_viewport`: front, side, back, top, three_quarter, current. Capped at 4 images per call, as captures are. |
| `renderer` | `"arnold"` | or `"hw2"` (mayaHardware2). |
| `resolution` | 512 | clamped 64–2048. Lower than capture's 768: these frames cost seconds, not milliseconds. |
| `isolate` | `None` | list of object names; frames them and hides everything else. |
| `samples` | 3 | Arnold AA samples, 1–8. Ignored by hw2. |
| `fallback_light` | `True` | add a temporary key light when the scene has no renderable light. |

**Returns** `capture_viewport`'s shape — `images: [{angle, png_b64}]` and
`camera_positions` — plus, per image, `opaque_px`, `total_px` and
`distinct_colors`, and the renderer actually used.

### Why arnold is the default

The failure this ticket exists to kill is judging a gem as grey. A fast default
reintroduces exactly that failure and reintroduces it *silently*, because a
wrong-looking render is not obviously wrong. A slow default only costs time.
`hw2` stays one parameter away for when speed matters and the materials are
opaque.

### Why the pixel statistics are part of the contract

From the ticket: *report opaque pixel counts, not just success/failure — the
failure mode here is a blank image that looks like a successful call.* A render
of an empty or unlit scene returns a valid PNG and a success status. So the
statistics ride on every response, and a call whose images are **all** blank is
an error with a hint, not a success carrying black squares.

## 4. The five traps

The probe found these; the wrapper exists largely to close them.

1. **`cmds.render` overwrites one fixed path per call.** Both probe renders
   landed on the same `untitled.png`. Each angle gets a unique
   `imageFilePrefix`; the handler reads the returned path, copies the bytes out,
   and deletes the file.
2. **Render globals are scene state.** Renderer, image format, file prefix,
   resolution, device aspect ratio and Arnold's sample counts are all persistent
   attributes on the user's scene. A `_RenderGlobalsState` snapshot/restore
   mirrors `_PanelState` in `capture.py`: whatever the call touches, it puts
   back.
3. **No panel means no `viewFit`.** `capture.py` places a camera from pure bbox
   math and lets `viewFit` refine the framing, which needs a model panel.
   Headless, the math has to stand alone — so the temp camera's focal length is
   set explicitly from the 40° field of view that math already assumes, rather
   than left at Maya's default 35 mm. This is a pure function and is tested
   headless.
4. **`isolate` cannot be panel isolate.** Panel isolation is a viewport concept
   and invisible to a render. Here it means hiding the non-targets and restoring
   their visibility in a `finally`.
5. **Arnold on an unlit scene renders black**, which is indistinguishable from
   a broken render. `fallback_light` adds a temporary key when the scene has no
   renderable light and removes it afterwards.

Two further notes carried from the probe: Arnold at default samples is noisy and
under-lit, which is why `samples` is exposed at all; and if `arnold` is
requested but absent from `cmds.renderer(q=True, namesOfAvailableRenderers=True)`
the call fails with a hint pointing at `hw2`, rather than silently substituting a
renderer that cannot answer the question being asked.

## 5. Structure

New module `maya_plugin/handlers/render.py`, following the house split: pure
math and validation at the top, tested headless; the Maya-touching part isolated
below it. It imports `capture.camera_placement` and `capture._scene_bbox` rather
than restating the framing math — one placement model, two backends.

Pixel statistics live in `src/maya_mcp/images.py` beside the existing downscale
and contact-sheet helpers, as a pure Pillow function over PNG bytes. The plugin
side cannot be assumed to have Pillow; the server side already requires it.

The tool registration in `src/maya_mcp/server.py` follows `maya_capture_viewport`
exactly, with its own longer timeout — an Arnold frame is seconds, not
milliseconds.

## 6. Verification

**Mechanical, headless (pytest):** focal-length-for-FOV math; angle, renderer,
resolution and sample validation; per-angle prefix uniqueness; pixel statistics
distinguishing a blank PNG from a lit one; the all-blank result raising rather
than returning.

**Judged, live** — `evals/render_scene_live.py`, run against a *disposable
agent-launched* Maya on port 9878, which is the configuration the whole ticket
is about. Its gate is the ticket's acceptance criterion:

1. a lit scene renders non-blank from a Maya with no mapped window, and
2. a transmissive gem measurably differs from an otherwise identical opaque one.

Both numbers are printed and the images kept as artifacts. A green pytest run
proves nothing here on its own — the headless suite happily agreed that
capture worked while it returned transparent images.

## 7. Also closed with this ticket

From the v4 gem-brute run, on #584: primitive kinds do not share a base size.
`polyCube` is 1 unit across while `polyPlatonicSolid` is radius-based, so the
same `scale` yields a solid twice as large and swapping `kind` silently doubles
the object.

The fix is normalisation, not documentation: every kind is built so `scale` means
the same width across all of them, and the tool description states that
guarantee. Documenting the discrepancy would leave the caller doing arithmetic
per kind, which is what the run already did wrong. This changes the size of
platonic solids and prisms produced by the current tool — acceptable, since the
current behaviour is the defect.
