# M2.4 — shape multipliers: the deformer set and arrays

**Status:** approved design, not yet planned
**Ticket:** redmine #587 (project 35, `maya-mcp`)
**Follows:** M2.2 the headless render path (#584, merged `4b427d9`) and M2.3 the
four look-dev findings (#586, merged `3a67b4c`)
**Evidence:** the #585 gem-brute art run (`evals/gem_brute_v5.py`, commit `356ea85`)

---

## 1. Why this exists

The art run produced a figure. It also produced a verdict about the toolset that
built it: **every chunk was a primitive with a scale and a rotation.** Twenty-seven
chunks, ten primitive kinds, nothing else. Two specific costs showed up in the
source of that eval, and both are toolset gaps rather than authoring mistakes.

**No taper.** A limb that is thick at the shoulder and thin at the wrist cannot
be expressed. The closest reachable shape is a uniformly scaled cylinder, so
every limb in the run is a uniformly scaled cylinder.

**No symmetry.** Each left/right pair is two literal rows in the chunk table,
hand-typed, hand-negated. Nothing enforces that they match; a typo in one row is
an asymmetric figure that nothing catches.

Neither gap is exotic. Both are the ordinary vocabulary of box modelling, and
their absence is the reason a 27-chunk figure needed 27 hand-authored rows.

### Why this rather than curves

Curve-based construction — `revolve`, `loft`, extrude-along-curve, `sweep` — is
the other obvious way to widen range, and it is deliberately **not** this
milestone.

- Deformers and arrays multiply the geometry that already exists. Every
  primitive, every boolean result, every etched mesh becomes a family of shapes.
  Curves add a parallel construction path that only produces what is explicitly
  built with it.
- The need here is observed, not predicted. The two gaps above come with a
  commit that demonstrates them.
- Both are verifiable by numbers, headless. Array placement is arithmetic on
  transforms; the one genuine correctness hazard (below) has a one-number test.
  Loft and revolve produce topology whose quality — poles, n-gons, normal
  continuity — needs a judged pixel loop or a human, which is a slower gate per
  tool.
- Curves cost infrastructure before they cost tools. A NURBS curve is a new
  object *type*, and `get_scene_graph`, `get_object_info`, the move ledger, and
  mesh cleanup all currently assume meshes.

Curves stay the next candidate. This milestone is the cheap multiplier.

## 2. Boundary

**In:** three new deformer types on the existing `maya_deform`, and one new tool
`maya_array` with three modes.

**Out, deliberately:**

- Curve construction of any kind (see above).
- Instanced copies. Array copies are real duplicates. Instances share a shape
  node, which breaks per-copy booleans, per-copy material assignment, and the
  move ledger's per-object identity — three systems that already work, traded
  for memory this project does not need.
- `polyMirrorFace` (mirror-and-merge into a single mesh). A different operation
  with a different failure surface — seam vertex merging, tolerance tuning.
  `maya_array`'s mirror produces a separate object; welding two halves into one
  is a later ask, and `maya_boolean_op` already covers the common case.
- Deformer *animation* — weights, membership editing, painted falloff.
- Nested or recursive arrays (an array of an array). Achievable by calling the
  tool twice on the group; not a mode.

## 3. Completing the deformer set

`maya_deform` ships five types: `bend`, `squash`, `twist` (via `cmds.nonLinear`),
`sculpt` (via `cmds.sculpt`), and `lattice` (via `cmds.lattice`). Maya's
`nonLinear` command offers six types; three are unreachable today.

| type | params | what it unlocks |
|---|---|---|
| `flare` | `curve`, `startFlareX`, `startFlareZ`, `endFlareX`, `endFlareZ`, `lowBound`, `highBound` | taper and bulge — a limb thick at the shoulder and thin at the wrist, a column with entasis, a wedge |
| `sine` | `amplitude`, `wavelength`, `offset`, `dropoff`, `lowBound`, `highBound` | linear ripple — corrugation, cloth folds, a wave down a length |
| `wave` | `amplitude`, `wavelength`, `offset`, `dropoff`, `minRadius`, `maxRadius` | concentric radial ripple — water rings, a shockwave, hammered metal |

`flare` is the one that closes an observed gap. `sine` and `wave` come with it
because they are the same code path and the same whitelist shape; excluding them
would be an arbitrary line.

Note `wave` has **no** `lowBound`/`highBound` — it is bounded radially by
`minRadius`/`maxRadius` instead. The whitelist is per-type precisely so this
kind of asymmetry is enforced rather than documented.

### The one refactor: set params by attribute, not by creation flag

Today the handler passes deformer params as flags to the creating command:
`cmds.nonLinear(mesh, type="bend", curvature=0.5)`. That works for the three
existing types because those three were verified live, but it leaves an open
question for every new type: is this name a command flag, an attribute, or both?

The three new types are added on a uniform path instead — create bare, then
`setAttr` each param on the deformer node:

```
node = cmds.nonLinear(mesh, type=deformer)[0]
for attr, value in dparams.items():
    cmds.setAttr(node + "." + attr, value)
```

Every `nonLinear` param in the table above is an attribute on the resulting
`deformBend` / `deformFlare` / `deformSine` / `deformWave` node under exactly
the name shown, so one path serves all six types and the flag question stops
existing. `bend`, `squash`, and `twist` move onto this path too — their existing
tests are the regression net for that move.

`sculpt` and `lattice` are **not** touched. They are different commands with
different return shapes and different verified behaviour (documented in
`sculpt.py` with a live-verification note each); folding them into a refactor
they do not need is risk for no gain.

Attribute names are verified in `mayapy` during implementation before any test
is written against them. Docs are the claim; the running Maya is the evidence.

## 4. `maya_array`

One tool, three modes. Every mode leaves the source object exactly where it is
and creates copies relative to it.

```
maya_array(name, mode, count, ..., name_prefix, group_name)
```

### The counting rule

`count` is the **total number of elements in the finished array, including the
source.** `count=12` on a gear tooth yields a 12-tooth gear: the source plus 11
copies. This is stated because the alternative reading — count as the number of
*new* copies — is equally defensible and silently produces off-by-one geometry
that looks almost right, which is the worst kind of wrong.

`mode="mirror"` ignores `count`; a mirror produces exactly one copy.

### `mode="radial"` — count, axis, center, angle

A radial array is the source **rotated about an axis through a center point**,
`count - 1` times. There is no radius parameter: the source's existing distance
from the center *is* the radius. This is both simpler and closer to how the
operation is actually used — place one tooth where it belongs, then say "twelve
of these".

Spacing depends on whether the sweep closes:

- `angle == 360` (the default): step is `360 / count`. A full ring has no
  element at the seam, because the seam is where the source already is.
- any other `angle`: step is `angle / (count - 1)`, so the first and last
  elements land on the arc's endpoints.

Both readings are correct for their case and wrong for the other, so the rule
is explicit and directly tested.

`axis` is `"x"`, `"y"`, or `"z"`; rotation follows the right-hand rule about
that axis. `center` defaults to the world origin.

Unlocks: gears, colonnades, spoked wheels, a crown of spikes, a rotunda, petals.

### `mode="linear"` — count, offset, step_rotate, step_scale

Copy `i` (for `i` in `1 .. count-1`) is the source displaced by `i * offset`,
rotated by `i * step_rotate`, and scaled by `step_scale ** i`.

Scale **compounds** rather than accumulating linearly. That is the deliberate
choice: compounding gives a geometric progression, which is what a tapering run
of ribs, a spire of diminishing blocks, or a receding row of columns actually
looks like. Linear accumulation reaches zero and then inverts, which is a
degenerate mesh rather than a taper.

Unlocks: staircases, fence posts, ribcages, vertebrae, ladder rungs, window
rows, a tapering tail.

### `mode="mirror"` — axis, pivot

One copy, reflected across the world plane perpendicular to `axis` through
`pivot` (default the world origin).

**This mode exists to encode a trap.** The obvious implementation — duplicate,
set `scaleX = -1` — is wrong twice over.

*Wrong for rotated objects.* Negating one scale channel on the object itself
composes as `T · R · S · M`, but a true reflection is `M · T · R · S`. Those are
equal only when the object's rotation commutes with the mirror, i.e. when the
object is unrotated or rotated only about the mirror axis. An arm rotated 30°
outward, mirrored this way, lands in the wrong orientation — subtly, plausibly,
and invisibly at thumbnail scale. So the mirror is applied via a temporary
parent group carrying the `-1` scale, which composes on the correct side.

*Wrong for winding.* Any negative scale inverts face winding order. Once frozen,
the mesh's faces point inward. Under Arnold that renders black or hollow; in the
viewport it reads as a lighting or material failure. It is neither. The handler
therefore freezes the transform (`makeIdentity`) and then reverses normals
(`polyNormal`), and the result is **measured**, not assumed.

Unlocks: every bilaterally symmetric thing, authored once.

### Common parameters

- `name_prefix` — base name for the copies; defaults to the source's short name.
  Each copy goes through the existing unique-name path, so collisions are
  impossible rather than merely unlikely.
- `group_name` — when given, all copies (and only the copies) are parented under
  a new group. The source stays where it is in the hierarchy; silently
  reparenting the user's object would be a surprise.
- Every copy is recorded in the move ledger, exactly as `maya_duplicate` does, so
  later live-user-edit detection works on array output.

### Result

`ArrayResult`: `names` (canonical long names of the copies, in array order),
`mode`, `group` (long name or null), `signed_volume` (mirror only), `warnings`.

## 5. Signed volume: the instrument for the winding trap

A closed mesh's signed volume is the sum over its triangles of
`dot(a, cross(b, c)) / 6`. For consistent outward winding it is positive; invert
the winding and every term flips, so it is negative. Magnitude is the actual
volume.

This is exactly the right instrument for the mirror trap: one number, computed
from geometry, that is positive when the operation succeeded and negative when
it produced the plausible-looking failure. It cannot be fooled by a render that
happens to look fine at the angle that was checked.

The handler computes it on the mirrored copy after the normal reversal, returns
it, and attaches a loud warning if it is not positive. The pure function is
tested headless against hand-computed tetrahedra and cubes in both windings.

It is reported only for `mirror`. The other modes are rigid rotations and
translations of an already-correct mesh; there is nothing there for it to catch,
and computing it anyway would suggest otherwise.

## 6. Architecture

Unchanged from the house pattern: pure math tested headless, Maya-touching code
kept thin and isolated.

| file | responsibility |
|---|---|
| `maya_plugin/handlers/arraymath.py` (new) | Pure. Angle sequences, per-copy transform deltas, bbox reflection, signed volume. No `cmds` import. |
| `maya_plugin/handlers/array.py` (new) | Maya-touching. Duplicate, place, mirror-and-fix-winding, group, ledger. |
| `maya_plugin/handlers/sculpt.py` (modify) | Deformer whitelist gains three types; `nonLinear` params move to `setAttr`. |
| `maya_plugin/maya_mcp_plugin.py` (modify) | Register the `array` handler. |
| `src/maya_mcp/schemas.py` (modify) | `ArrayResult`. |
| `src/maya_mcp/server.py` (modify) | `maya_array` tool; `maya_deform`'s param docs gain the three types. |
| `tests/test_arraymath.py` (new) | The pure layer, exhaustively. |
| `tests/test_array.py` (new) | The handler against a `FakeCmds`. |
| `evals/array_deform_live.py` (new) | The live acceptance gate. |

The `FakeCmds` pattern from `tests/test_render.py` carries over, including its
governing principle: the fake must reproduce Maya's *lies*, not its
documentation. That fake caught the short-name/long-name isolate bug in M2.2 only
after it was corrected to return short names the way Maya actually does.

## 7. Acceptance

Headless tests are necessary and not sufficient — they prove the arithmetic, not
that Maya did what the arithmetic says. `evals/array_deform_live.py` runs against
the disposable Maya on port 9878 and builds three objects that are impossible
with today's toolset:

1. **A gear** — one tooth, `radial(count=12, axis="y")`. Asserts twelve distinct
   objects, twelve distinct world centroids, and every centroid equidistant from
   the center to within tolerance.
2. **A tapered ribbed spine** — one rib, `linear(count=9, offset, step_scale)`,
   plus a `flare` on the core. Asserts monotonically decreasing bounding-box
   width along the run, and that the flare changed the core's bbox in the
   expected direction.
3. **A bilaterally symmetric torso** — an asymmetric, *rotated* chunk,
   `mirror(axis="x")`. Asserts the mirrored bbox matches the pure prediction,
   and that `signed_volume > 0`. The source is deliberately rotated, because an
   unrotated source cannot distinguish the correct implementation from the naive
   one.

All three are then rendered through `maya_render_scene` and asserted non-blank,
which is the end-to-end proof that the geometry is real, lit, and outward-facing.

The gate is a script that exits non-zero on failure, in the shape of
`evals/render_scene_live.py` and `evals/lookdev_controls_live.py`.

## 8. Risks

**`makeIdentity` on a negatively-scaled group.** The freeze step is the load
-bearing part of the mirror. If Maya declines to freeze it, or freezes it
without baking the reflection, the mirror silently degrades to a translation.
The signed-volume check catches the winding half of this; the bbox assertion in
the live gate catches the placement half. Both run before merge.

**Attribute names for the three new deformer types** are taken from Maya's
documentation and verified in `mayapy` before any code depends on them. If a
name is wrong, `setAttr` raises immediately with the node name — a loud failure,
not a silent no-op.

**`cmds.rotate` with a world-space pivot** is the placement mechanism for radial
arrays. It is well-trodden, but the composition of a pivot rotation with an
already-rotated source is exactly the class of thing this spec assumes wrong
elsewhere, so the gear gate asserts equidistance rather than trusting it.
